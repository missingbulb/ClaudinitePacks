How this reads your repo

Everything happens in this browser tab. The page calls api.github.com directly as you, so your own GitHub permissions are the only access control — there is no backend, no shared credential, and this page can show you nothing your account cannot already read. Your credential is held for this tab only (sessionStorage) and is sent to GitHub and nowhere else.

Where sign-in is configured, Sign in with GitHub authorizes once and everything afterwards runs as you. Otherwise the page falls back to a pasted token, which needs read-only Contents, Issues and Actions.

Responses are cached in this browser: repo content is keyed by commit SHA, live data is revalidated with ETags (a 304 costs no rate limit), and settled history ages out after 24 hours. Clear cache forces a cold read. Pass ?repo=owner/name to jump straight to a repo.

What Claudinite did for this fleet this week

The work the machinery did that nobody had to do — in a window, this week against last, because a total that only ever grows tells you nothing about today. Every figure is a count of things that individually happened, from reads this page already makes. There is no estimate of hours saved and no score: nothing here measures those, so nothing here claims them.

Fleet at a glance

Each tile counts members, never things. "47 open items" is not a number anyone acts on; "3 members need you" is — it is the length of this morning's list. A tile is coloured only when it is reporting something, so a coloured tile always means look here.

The last two mornings

The fleet's own morning brief — what the fleet accomplished that day, and the project worth returning to — written by the digest task into the enforcer repo, one file per day. A day with no brief is a normal state: the task had nothing to report, or has not run yet. Both files are content at a path, so a warm load costs nothing to show them.

Fleet activity

Every other panel here answers where do I need to look, and after a good week they are all zero — which is exactly what a dead fleet looks like too. This is the other reading: what happened, per day. Every figure comes from reads the page already makes, so the panel costs no extra request; what that costs instead is depth, and where a series runs past what one page of issues or thirty runs can see it says so rather than drawing a confident zero.

Members — worst first

Ordered by the worst thing that is true of each member, not by how much it has. One item parked for a human outranks forty healthy ones, because the first needs you today and the second is the system working. A member that cannot be read, one that does not run Claudinite, and one that is fine are three different rows and never collapse into a zero.

The columns are grouped as three questions: Status — what kind of repo this is and whether it is alive; Claudinite — what the machinery is doing here; Work — what is waiting on a person. Every column comes from a read this page already makes, which is also why four things are missing: rule tokens, test counts and time saved would each need a member's own files read, and conversation-log sessions a branch listing. Issues and pull requests are counted within the issue window — the most recent hundred — so an older one is not counted rather than counted wrongly.

Tasks across the fleet

The one question no single repo's page can answer. A task ships from a shared pack, so it runs in every member that declares it — and the same task parked in four members at once is a canon problem, while in any one repo it looks like that repo's bad luck.

A shared pack's task, everywhere it runs. One parked in several members at once is the pack's problem, not any one member's.

Pack adoption

Who a change to a pack would reach. Before editing a pack's rules or its checks, this is the blast radius; after, it is how many members have to converge before the change is real.

This repo at a glance

Parked and past a leash are the two that mean work has stopped: the first is waiting on a person, the second has been sitting in a machine state longer than its cadence allows. The rest are context for reading those two.

Task roster — every declared task

Every declared task gets a row, including one that has never run — which is usually the thing you opened this for. A list derived from the work items would omit it silently, and a task that never fired looks identical to one that has nothing to do.

Queue — open work items

One open issue per piece of scheduled work, labelled with the state it is in. Idle is how long it has sat in that state: a long idle in a machine state is the queue stuck, and a long idle in needs human is you.

Scheduler runs

The Actions runs behind the queue. A run that fails is not the same as a task that fails — the first means the scheduler never got to decide anything, which is why a member whose runs are red reads as broken even when every task looks healthy.
